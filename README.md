# Магия — персональные иллюстрированные сказки

B2C-сервис: родитель заполняет короткий конструктор, оплачивает заказ, а сервис
создаёт персональную книгу (8–10 глав, обложка и 3–5 иллюстраций), собирает PDF
с кириллицей и отдаёт готовую книгу по личной ссылке. Заказ и результат доступны
без регистрации.

Стек: **Next.js 15 (App Router) · React 19 · TypeScript · Zod · PDFKit · sharp ·
Supabase (PostgreSQL + private Storage)**. Без Docker, Redis и Kubernetes.

---

## 1. Быстрый старт (локальная разработка)

```bash
npm install
cp .env.example .env.local     # Windows: copy .env.example .env.local
# в .env.local обязательно задайте ORDER_ACCESS_SECRET (≥ 32 символов):
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
npm run dev
```

Откройте http://localhost:3000. В локальном профиле по умолчанию включён
демо-режим: сказка и иллюстрации создаются детерминированным локальным
генератором, оплата подтверждается кнопкой на странице `/pay/<id>`, письма
складываются в `data/outbox/*.json`. Демо-книга всегда помечается
«ДЕМО-ВЕРСИЯ» в интерфейсе и в PDF — выдать её за результат реальной
AI-генерации нельзя.

> Демо-режим (`DEMO_MODE=true`) и тестовая оплата (`PAYMENT_PROVIDER=test`)
> допустимы только вне production. Приложение само проверяет это при старте
> и отказывается работать с небезопасной конфигурацией.

## 3. Production: Supabase (PostgreSQL + private Storage)

1. Создайте проект Supabase.
2. Примените миграцию `supabase/migrations/0001_init.sql` (SQL Editor или
   `supabase db push`). Миграция создаёт таблицы `orders` и `payments`,
   индексы, приватный bucket `magia-private` и включает RLS.
3. Заполните `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` (только серверные
   переменные, никогда не отдавайте service-role ключ в браузер).

**Модель безопасности БД.** На `orders` и `payments` включён RLS **без единой
политики** — это deny-by-default: роли `anon` и `authenticated` не могут
читать и писать ничего. Приложение работает с базой только серверным
service-role ключом. Иллюстрации и PDF лежат в приватном bucket: публичных
объектов нет, сервер стримит их только после проверки личного токена заказа.
Если вы решите открыть таблицы через anon-ключ, добавляйте узкие политики, а
не отключайте RLS.

**Локальный fallback.** Если `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` не
заданы, приложение использует файловое хранилище: заказы — `data/db.json`,
файлы — `data/storage/`, письма — `data/outbox/`. Каталог `data/` в
`.gitignore`; это режим разработки, не для production.

## 4. Генерация сказок и иллюстраций

- Текст: любой OpenAI-совместимый chat-провайдер (`AI_TEXT_BASE_URL` +
  `AI_TEXT_API_KEY` + `AI_TEXT_MODEL`).
- Иллюстрации: `IMAGE_PROVIDER=openai` использует image-API
  (`AI_IMAGE_*`), `local` рисует встроенный детерминированный иллюстратор
  (SVG → JPEG через sharp) и работает без интернета. Если внешний
  провайдер изображений недоступен, пайплайн автоматически падает обратно на
  локальный иллюстратор и добавляет честное предупреждение в результат.
- Провайдеры не зависят друг от друга: сбой изображений не ломает текст, а
  ошибки генерации повторяются до `GENERATION_MAX_ATTEMPTS` раз без повторной
  оплаты.
- Ответ модели проверяется по схеме (Zod): 8–10 глав, 3–5 сцен, ограничения
  длины. Markdown, HTML, ссылки и кодовые обёртки вычищаются; контент
  проверяется на недопустимые для детской книги темы. Данные заявки передаются
  как недоверенный материал в отдельном теге: инструкции внутри заявки
  игнорируются (защита от prompt injection), внешние картинки генерируются без
  текста и водяных знаков.
- Персональные данные ребёнка не уходят в лог, а заказ из демо-режима
  навсегда остаётся демо, даже если окружение потом изменится.

## 5. Оплата

- `PAYMENT_PROVIDER=test` — только для разработки (в production запрещён на
  уровне конфигурации). Платёж подтверждается серверным эндпоинтом
  `/api/orders/[id]/test-pay` после проверки токена заказа.
- `PAYMENT_PROVIDER=yookassa` — реальная оплата. Создание платежа и проверка
  статуса выполняются на сервере через API ЮKassa
  (`YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`); вебхук
  `/api/payments/yookassa/webhook` и периодическая сверка статуса подтверждают
  оплату только при совпадении суммы, валюты и заказа. Браузеру не доверяем:
  «оплачено» из клиента игнорируется.
- Идемпотентность: повторные подтверждения платежа не создают дублей, повтор
  генерации после сбоя не требует повторной оплаты (`POST .../retry`).

## 6. Обработка очереди: inline, cron или отдельный воркер

Оплаченный заказ превращается в «queued»-задачу. Обработать её можно тремя
способами:

1. **Inline-воркер** (`INLINE_WORKER=true`) — задача подхватывается веб-
   процессом через `after()` после ответа API. Удобно для разработки; в
   production ненадёжно (процесс может умереть).
2. **Cron** — внешний планировщик раз в минуту вызывает
   `GET /api/cron/worker` с секретом:
   `Authorization: Bearer $CRON_SECRET` (или `x-cron-secret`). Подходит для
   serverless-хостинга.
3. **Постоянный воркер** — `npm run worker` (или
   `npx tsx scripts/worker.ts --interval=5000`). Рекомендуется для VPS.

В production используйте вариант 2 или 3 и выключите inline-воркер
(`INLINE_WORKER=false`).

Статусы заказа: `pending_payment → paid → generating → completed`, плюс
`failed` (с повтором) и `refunded`.

## 7. Личный доступ к заказу и удаление данных

- Регистрация не нужна. При создании заказа генерируется 256-битный токен.
  В базе хранятся только SHA-256-хэш (для проверки) и AES-GCM-шифротекст
  (чтобы восстановить ссылку в письме) — открытого токена в базе нет.
- Токен передаётся в ссылке `/order/<id>?token=...` или заголовке
  `x-order-token`. Клиент переносит его в `sessionStorage` и вычищает из
  адресной строки, чтобы ссылка не утекла через историю.
- `/order/[id]` и `/pay/[id]` закрыты от индексации (noindex + robots), API
  отвечает `Cache-Control: no-store`.
- Восстановление: `/recover` — номер заказа + e-mail, на который придёт
  письмо с новой личной ссылкой.
- Удаление данных: кнопка на странице заказа удаляет персональные данные,
  иллюстрации и PDF и обнуляет токен доступа — ссылка перестаёт работать.
- Точечные ограничения частоты запросов (`lib/security/rate-limit.ts`) стоят
  на создании заказа, восстановлении, оплате и выдаче файлов.

## 8. Документы и юридические плейсхолдеры

Страницы `/legal/privacy`, `/legal/consent`, `/legal/terms`,
`/legal/requisites` — рабочие тексты с **явно помеченными плейсхолдерами**.
Перед публикацией их обязательно нужно заменить на реальные данные:

- продавец и реквизиты (ИП/ООО, ИНН, ОГРН/ОГРНИП, адрес);
- контакт поддержки (`SUPPORT_EMAIL`, по умолчанию `support@magia.example`);
- отправитель писем (`EMAIL_FROM`, по умолчанию `Магия <hello@example.com>`);
- сроки, порядок возврата и юридически значимые формулировки согласий.

Ничего из этого не выдумано намеренно: тексты дают структуру и оставляют
места для данных продавца.

## 9. Тесты

```bash
npm test
```

Покрыто: гостевые токены (хэш, AES-GCM, подделка), валидация заявки,
санитайз ответа модели (markdown, обрезка, недопустимые темы, подмена сцен),
демо-генератор (все темы, схема, отсутствие рода и склонения имени),
сборка PDF (число страниц, метаданные, кириллица) и полный жизненный цикл
заказа на локальном репозитории: создание → токен → оплата → генерация →
письмо → идемпотентность → удаление данных.

Ручная проверка (Chrome/Safari):
создать заказ на `/create` → оплатить на `/pay/<id>` → дождаться генерации на
`/order/<id>` → скачать PDF → проверить кириллицу и отсутствие обрезки → нажать
«Удалить данные» и убедиться, что ссылка перестала открываться.

## 10. Структура проекта

```
app/                 страницы (/, /create, /order/[id], /pay/[id], /recover, /legal/*)
app/api/             REST: заказы, оплата, PDF/иллюстрации, cron, health, config
components/          UI: конструктор, страница заказа, оплата, восстановление
lib/config.ts        единая конфигурация и проверки безопасности окружения
lib/orders/          домен заказов: сервис, локальный и Supabase-репозитории
lib/generation/      пайплайн: провайдеры текста/картинок, санитайз, воркер
lib/pdf/             вёрстка книги (обложка, главы, финал, письмо, сертификат)
lib/illustration/    локальный векторный иллюстратор
lib/security/        токены, шифрование, rate limit
lib/storage/         локальное и Supabase-хранилище файлов
supabase/migrations/ SQL-схема, RLS, приватный bucket
scripts/             ассеты и воркер
tests/               Vitest
```

## 11. Что осталось за рамками MVP

- Каталог: реально работает только «Персональная сказка»; остальные форматы
  помечены «Скоро».
- Возвраты (`refunded`) support-команда проводит вручную в кабинете ЮKassa.
- Нет админ-панели: заказы смотрят через SQL/логи.
- Удаление данных доступно на странице заказа; выгрузка по отдельному
  запросу — через поддержку.
